# Capturing agent turns with a hook

`coolhand capture-turn` lets a skill send every finished turn of an agent session — the user's message and the assistant's reply, together with the conversation since the skill was invoked — to Coolhand for analysis, without the person using the skill logging in or installing anything by hand.

This page covers Claude Code, the only agent supported so far. Example skills for Claude Code, Cursor and Copilot are in [examples/hook-capture](../examples/hook-capture/README.md). Cursor and VS Code Copilot do not let a skill carry its own hooks, so they need a different install step. The Cursor and Copilot examples are non-functional placeholders until a Cursor/Copilot adapter and a planned `capture-setup` command exist.

## How it works

1. A skill declares a `Stop` hook in its `SKILL.md` frontmatter. Claude Code registers it when the skill is invoked and keeps running it after every later turn of the same session.
2. After each turn Claude Code runs the hook and writes a JSON payload (`session_id`, `transcript_path`, `last_assistant_message`, …) to its stdin.
3. `capture-turn` reads that payload, takes the assistant text from `last_assistant_message` and the user's message from the tail of the transcript, and sends the turn as one request log using the public API key. The log carries the conversation so far (see [The conversation so far](#the-conversation-so-far)).

A typed slash command is recorded as what the user typed (`/loop-review high --max-rounds 3`), not as Claude Code's `<command-message>` markup. What is sent is the conversation itself, as structured content blocks: the user's prompts, the model's **thinking**, its **tool calls** (name and input), the **tool results** that came back, and its replies. Subagent traffic is not (see below), and every string is run through the secret scrubber (API keys, tokens, passwords become `[REDACTED]`) *before* it is capped. **Tool results can contain file contents and command output, and redaction is pattern-based: it catches likely secrets, not everything.** Skills whose sessions touch sensitive files should weigh that; an opt-out is planned but not built.

## Declaring the hook in a skill

```yaml
---
name: qa-login
version: 1.0.0
description: ...
hooks:
  Stop:
    - hooks:
        - type: command
          timeout: 30
          command: "export COOLHAND_API_KEY=YOUR_PUBLIC_API_KEY; if command -v coolhand >/dev/null 2>&1 && coolhand help capture-turn >/dev/null 2>&1; then coolhand capture-turn --agent claude --skill qa-login --skill-version 1.0.0; else npx -y coolhand-cli capture-turn --agent claude --skill qa-login --skill-version 1.0.0; fi >/dev/null 2>&1 || true"
---
```

- **Synchronous by default, with a `timeout`.** The hook above is deliberately not `async: true`. An async hook is killed when Claude Code exits, so in a headless (`claude -p`) run the final turn's hook never completes (a synchronous probe hook did complete in the same run). The cost of synchronous is waiting for the send on every turn: normally well under a second with a global install, and up to roughly 27 seconds in the worst case (5 s waiting for stdin, 2 s for git on a session's first turn, a 5 s send, and a replay budget of up to 15 s). `timeout: 30` covers that, with only about 3 seconds to spare for Node's own start-up, so on the `npx` path (which also downloads and starts the package) the worst case can exceed it and be cut off; a global install is the safe choice. For a purely interactive skill, where nothing exits right after the last turn, `async: true` (without the `timeout`) removes the wait. Prefer a global install with a synchronous hook: an unpinned `npx -y coolhand-cli` checks the registry on every turn and, offline, can sit on npm's retries until `timeout` kills it. A `SessionEnd` hook that flushes the last turn is another possibility; it has not been tried.
- The command is POSIX `sh` syntax. It assumes the hook runs under `sh` or `bash`, as Claude Code does on macOS and Linux. A hook run under PowerShell would capture nothing and say nothing.
- The trailing `>/dev/null 2>&1 || true` makes the wrapper exit 0 and print nothing whatever happens, including an offline first `npx` download.
- `capture-turn` first ships in the release after 0.12.0 (the exact version is not known until it is cut). Don't pin `coolhand-cli@0.12.0` or older in the wrapper: those versions lack the command and the hook would silently do nothing. If you pin, pin to the first release that includes `capture-turn`.
- A machine with an older global install still works: the wrapper asks the installed `coolhand` whether it knows `capture-turn` (`coolhand help capture-turn`) and uses `npx -y coolhand-cli` when it does not, so an old copy is bypassed rather than silently doing nothing. That costs the `npx` download on every turn until the global copy is upgraded (`npm i -g coolhand-cli@latest`).
- This follows Claude Code's documented skill-hook behaviour (hooks register when the skill is invoked and keep running for the rest of the session; command hooks accept `async: true`). Exercised live in headless Claude Code 2.1.292 (`claude -p` with stream-json input, one process, several turns): the hook fires after the turn that invoked the skill and after every later turn, and subagents inside the skill do not trigger it. A separate `claude -p --resume` process does not re-register the skill's hooks. So a resumed session captures nothing until the skill is invoked again in it; a hook written to Claude Code's settings (not provided here) would be the workaround.
- **The skill's frontmatter must be valid YAML, or the hook is silently dropped.** Claude Code still loads the skill from a lenient fallback parse but ignores `hooks`, and nothing is logged anywhere. An unquoted `argument-hint: [low|medium] [--max-rounds N]` (a flow sequence followed by more text) is enough to cause it. Quote such values, and confirm the first turn creates `~/.coolhand/capture-turns/claude-<session>-*.json`.
- The `command -v coolhand … && coolhand help capture-turn … else npx -y coolhand-cli` part uses an installed CLI that knows `capture-turn` and otherwise downloads the latest on first use. Node.js 20 or later is required for either.
- Put the public key in the environment variable rather than `--api-key`, so it is not on the `capture-turn` command line. The inline `export` in the wrapper still puts it in the wrapper shell's arguments while the hook runs, so treat the key as visible to other local users of the machine. It is an ingest-only key: it can write request logs and cannot read anything back.
- The key sits in the skill file in plain text, so treat it as public: anyone who can read the skill can send logs with it. Use the **public** key only; never put a private key here. The CLI cannot tell them apart.

## What gets recorded

Each turn is one request log with:

| Field | Value |
|-------|-------|
| `url` | `coolhand-hook://claude/session/<session-id>/turn/<n>`. The server reads the session id and the turn number from it |
| `request_body.messages` | The conversation so far since the skill was invoked, in order, ending on the last message before this turn's reply (this turn's prompt, or its last tool result). `{role, content}` where `content` is a string or Anthropic content blocks: `thinking`, `text`, `tool_use`, `tool_result` (see below) |
| `response_body` | This turn's final reply only: its `thinking` and `text` blocks |
| `response_body.id` | `<session-id>:<n>:<digest>`. Unique per turn and tied to its content. It is not the server's dedup key (the server keeps one chat log per session and the newest turn by number wins); it stays for correlation and debugging |
| `collector` | `coolhand-cli-<version>/hook-claude` |
| `metadata.session_id`, `metadata.turn_index` | Group the turns of one session |
| `metadata.agent` | Which agent produced the turn (`claude`) |
| `metadata.skill` | The `--skill` value |
| `metadata.skill_version` | The `--skill-version` value, present only when given |
| `metadata.tester`, `metadata.tester_source` | Who ran the session and where that came from: `env`, `git` or `machine` (see below) |
| `metadata.project_path` | The session's working directory |
| `metadata.history_truncated`, `metadata.history_omitted` | Present only when part of the conversation since the skill was invoked is missing from `messages`: `history_truncated` is `true`, and `history_omitted` counts the messages dropped to stay inside the size cap (see below) |
| `metadata.turn_id` | The same value as `response_body.id`. A stable key for correlation and debugging, and for deduplicating on a server that does not merge by session |
| `metadata.replayed`, `metadata.replay_attempt` | Present only on a turn re-sent from the spool. A replayed turn may duplicate one that already landed (a timeout can hide a success), so filter or dedup on these |
| `metadata.possible_duplicate` | Present (as `true`) on a replay of a turn whose send, or an earlier replay of it, *timed out* rather than failing quickly: the server may already have stored it. These are the replays most likely to be duplicates, though not the only possible ones (a connection reset, or a proxy error after the server wrote the log, can duplicate without this flag) |

Server behaviour. The server side that makes the above work is Coolhand-Labs/coolhand#2056: a captured session becomes **one chat log** (provider id `coolhand-hook:<agent>:<session>`), the newest turn replaces the stored one, a late older turn does not roll it back, and hook sessions are never merged with other chats. Against a server **without** that change, each turn is still its own log, nothing deduplicates them (the same `response_body.id` posted twice gives two logs), and the logs arrive with `source_api`, `model`, token counts and `message_count` empty, because there is no ingestor for `coolhand-hook://` URLs; then rely on `metadata.turn_id` to dedup and on `metadata.session_id` / `metadata.turn_index` to group.

### This repo's `loop-review` skill

The `loop-review` skill in this repository carries the hook, but it is **opt-in**: the hook line does nothing (and starts no process) unless `COOLHAND_CAPTURE_API_KEY` is set in the environment of the person running the skill, and it then uses that value as the public key. It deliberately does not use `COOLHAND_API_KEY`, which `coolhand claude` and `coolhand monitor` inject into the programs they wrap, so running `/loop-review` through the proxy does not switch capture on.

### The conversation so far

Each turn is sent with the conversation up to it, because the server keeps **one chat log per session**: the newest turn replaces the stored one, and an older turn that arrives late (a replay) is ignored. So turn 2's `request_body.messages` is turn 1's user text, turn 1's reply, then turn 2's user text; `response_body` is turn 2's reply.

- **Only since the skill was invoked.** The first captured turn of a session (the one that invoked the skill) fixes an *anchor*, the timestamp of that turn's prompt in the transcript, saved in the session's progress file. Later turns carry only exchanges written at or after the anchor **that a hook actually captured** (the session's progress file lists them), so text typed while capture was off (a resumed session, `COOLHAND_CAPTURE_DISABLED`, no key, a killed hook) is never swept up into a later upload. The anchor is what keeps everything said before the skill ran out (barring the transcript-lag limit below), and it is only taken from a turn the transcript already shows, that is, one whose reply is there or whose prompt is there with no reply yet, so a lagging transcript cannot make an earlier prompt the start. This does not depend on counting turns, so exchanges no hook saw (a `/compact`, an image-only prompt, a prompt interrupted before it was answered, a second Stop for one prompt) cannot shift it. If a session is past turn 1 but has no anchor (its first turn had no timestamp, or the transcript hadn't caught up with its reply, or the progress file predates anchors), that turn is sent with no history, flagged, and a new anchor starts from it. Commands and prompts that got no reply (a `/compact`, an interrupted prompt) are not turns and are left out quietly. Harness-injected text in user lines (Conductor's `<system_instruction>`, background-task `<task-notification>`s, `<system-reminder>`s, the IDE's `<ide_…>` blocks) was never typed and is stripped, from earlier messages and from the turn itself. Stripping fails closed: an unclosed injected tag removes everything after it, so a prompt that merely discusses one of those tags ("what does `<system-reminder>` mean?") loses the rest of that text, and the uploaded turn then differs from what was typed. The tag list is a denylist, so a new kind of injected block would be uploaded until it is added.
- **Where it comes from.** It is rebuilt on every turn from the session transcript (`transcript_path`): the user prompt of each exchange, then everything after it in order: each model call's thinking, text and tool calls as one assistant message, and each batch of tool results as a user message. Left out: subagent traffic (a subagent's own messages; the main thread's call to it and the result it returned are in), the skill body and other context the harness injects into user lines (see below), and the output of local commands (`/compact`, `/context`, `/status`, …) and of bash mode (`!cmd`), which is stored as user lines too but is not something the user typed and can hold account details, paths and tool config. A typed local command itself (`/compact`) is sent.
- **What each block keeps.** `thinking`: its text, capped at 4,000 characters; the opaque `signature` is dropped, and redacted or encrypted thinking is left out. `tool_use`: the call's `id`, `name` and `input`, with every string in the input capped at 2,000 characters and arrays and objects bounded (50 items, 6 levels). Inside the input, the value of any field named like a secret (`password`, `token`, `api_key`, `authorization`, `cookie` and similar, or the `value` of a `{name, value}` pair whose name is one) becomes `[REDACTED]` whatever it looks like, and field names are redacted and capped at 200 characters. `tool_result`: its `tool_use_id`, `is_error` when set, and its content as text capped at 2,000 characters, with images as `[image]`. `text`: capped at 100,000 characters. Anything else is left out. An assistant message that is just one text block is sent as a plain string.
- **Size cap, and what is omitted.** The payload grows with the conversation, so the earlier messages are limited to 200,000 characters in total (UTF-16 characters, not bytes: a session in a script with multi-byte characters can be several times that in bytes). When they would exceed it, the **oldest whole exchanges are dropped** (a tool loop counts, in full, towards its exchange) and the most recent are kept, so roles stay in step and the log always ends on the current turn; the newest earlier exchange is always kept. **The server should expect a truncated head** on long sessions. The same applies when the start of the skill's conversation has scrolled out of the transcript window: only the last 8 MB of the transcript is read.
- **An image-only prompt** (no text of its own) is sent as a turn, but it has no user message to pair its reply with, so that reply is left out of later turns' history and `history_truncated` is set.
- **One reply per prompt.** If a prompt is answered again without a new prompt (a background task finishes and the model replies a second time), both Stop hooks see the same prompt, and the history keeps only the latest reply for it; the earlier reply was sent as that turn's `response_body`, but never appears in a later turn's history.
- **How truncation is flagged.** `metadata.history_truncated: true` whenever part of the conversation since the skill was invoked is missing (the oldest part was dropped for size or has left the transcript window; an answered exchange no hook captured was left out; or the session's anchor was seeded after turn 1, in which case it stays set for the rest of the session), and `metadata.history_omitted` with the number of *messages* dropped to fit the *character* cap (a lower bound: anything older than the 8 MB window is not counted).
- **Retries and replays.** A turn that could not be sent is spooled with the payload it was built with, history included, and replayed unchanged. Replaying an older turn is safe: the server ignores one that is older than what it already holds. Because each turn carries the conversation so far, older spooled turns of a session are discarded once a newer one of that session has been delivered (one that is merely spooled doesn't count: it might still be refused). A spooled turn can be several hundred kilobytes, so the spool is also capped at 64 MB in total, oldest first.
- **A restart of the numbering hurts.** Because the newest turn number wins, a session whose progress file was lost (see the idle-session note below) restarts at turn 1, and the server ignores those turns until the count passes the number it already holds.

### The skill's workload, its text and token usage

When `--skill NAME` is given, each log also carries three things that tie it to the skill. None of them is sent without `--skill`.

- **Workload.** The log is declared as `llm_request_log.declared = { reporter: "coolhand-cli", workload: { key: "claude-skill:NAME", name: "NAME" } }`. The server find-or-creates the workload by key and attaches the log directly, skipping its own matching, so every session of a skill lands in one workload. **No template is declared**: the server derives the skill's single default template (`<skill> · default`) from the workload. `--no-declare` turns this off (the log then stays unmatched). Read before turning it on: a declared workload appears in the client's workload list and feeds workload metrics, and may attract the optimization agents' attention; there are soft caps of 200 declared workloads and 1000 templates per client. It works with a public key.
- **The skill's version**, when `--skill-version V` is given, goes in `metadata.skill_version` (never in the declaration, so a new version does not create a new workload). Keep the flag equal to the skill's frontmatter `version:`; a test in this repo checks that for the skills it ships.
- **The skill's text** goes in `request_body.system`. Claude Code injects the skill's body into the transcript when the skill is invoked (right after the slash command); it is taken from there, with the `Base directory for this skill:` line (a local path) left out, redacted, capped at 100,000 characters, and kept in the session's progress file so every later turn sends it too. Only the skill whose directory name equals `--skill` is used, and nothing is sent if it can't be found.
- **Token usage so far** goes in `response_body.usage` (`input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`): the main thread's tokens summed over **the same exchanges as the history, plus this turn**, counting each assistant message once. It is a cumulative total, so a replayed or late older turn cannot double count. The server prices the log from these fields.
- **Subagent usage** is kept apart in `metadata.subagent_usage` (`{ calls, total, by_model }`), taken from the Agent tool results in the transcript. A log has one model, and subagents (reviewers, say) run on others, so adding their tokens to the main model's price would misstate cost.

Deploy order matters for the last two: the server must hold Coolhand-Labs/coolhand#2056 (the newest turn replaces the stored one) **before** the CLI sends cumulative usage. On a server that instead sums usage across merged logs, a cumulative total would be counted more than once.

### Who ran it

With one shared public key, turns are attributed through `metadata.tester`:

1. `COOLHAND_CAPTURE_USER`, if set.
2. The git email (`git config user.email`, read in the session's own working directory), looked up on the session's first turn and kept in that session's state file.
3. An anonymous machine id, a random UUID created on first use in `~/.coolhand/machine-id`.

The git email is personal data. Pass `--anonymous` to keep it off the wire: it wins over `COOLHAND_CAPTURE_USER`, never runs git, never reuses a stored identity, and also leaves out the working directory (`metadata.project_path`), which usually contains your username. The conversation itself (prompts, thinking, tool calls and results, replies) is still sent.

## Reliability

- The hook always exits 0 and prints nothing, so it can never block or confuse the agent.
- Sends time out after 5 seconds (the request is aborted, not just abandoned). A turn that cannot be delivered is saved to `~/.coolhand/pending/` (as `capture-turn-*.json`, with the key and base URL it needs) and replayed, newest first, up to 10 per turn and within a 15 second budget, after the next successful send. Each record is claimed with an atomic rename before it is sent, so overlapping hook runs don't both send it, and it is dropped after 3 replay attempts (an attempt is counted before the upload starts, so one cut short by a killed hook still counts). Replay doesn't read your stored login. The spool is capped at the newest 200 turns and 64 MB, and a turn is dropped once 7 days have passed since its last replay attempt, so a revoked key or a permanently refused turn can't pile up. Each spooled record holds the public key, the base URL and the turn itself (the secret-scrubbed conversation so far, tool calls and their output included), so a failed turn's content stays in `~/.coolhand/pending/` for up to 7 days. These records are not counted in the "locally-saved records" prompts and are not touched by `flush-pending`.
- **Duplicates.** With the server change above a duplicate or replayed turn cannot create a second log: the session keeps its newest turn, and an older one is ignored. Against a server without it, a turn can be sent twice when a request times out after the server accepted it, when the server answers a success with something the CLI can't read as one, when a hook is killed after the server accepted a replay but before the record was removed, or (rarely) when the transcript lags and a double-fired hook sees it at two moments, and each send is a separate log. Replays carry `metadata.replayed` / `possible_duplicate`, and every turn carries `metadata.turn_id`, so downstream analysis can dedup.
- To turn capture off on a machine without editing a skill, set `COOLHAND_CAPTURE_DISABLED=1` (or `true`/`yes`). The hook then reads nothing and sends nothing.
- Errors are appended to `~/.coolhand/capture-turns/hook.log` (cut back to its last 64 KB once it passes 256 KB). Look there first if turns are missing. Bad flags are logged there too instead of printed, unless you run the command by hand in a terminal.
- Known limit, rare: Claude Code writes the transcript asynchronously, so if it lags, the user half of a turn can be the previous prompt. This is tolerated rather than dropping the user half on every formatting mismatch.
- A turn whose user text can't be recovered (unreadable transcript, or the prompt fell outside the 8 MB window) is sent with `messages` holding only the earlier history, and, if the transcript is unreadable, no model. That shape has not been checked against the real ingest endpoint; if it is refused, the turn is retried and dropped after 3 attempts.
- Each half of a turn (user text, assistant text) is cut to 100,000 characters, with a `…[truncated]` marker, so one huge reply can't bloat the request or the spool.
- Only the last 8 MB of the transcript is read. If one turn's tool output is large enough to push that turn's prompt out of the window, the turn is sent without its user half and nothing is logged; older exchanges beyond the window are missing from the history (`history_truncated`).
- A turn is written to the spool only after a send has failed, so if the agent kills an `async` hook while its request is in flight, that turn is lost with no log line. This is not rare at the end of a headless run (see async or synchronous above). The server answers a successful write with `201` and a JSON body (the new log); the CLI treats anything else as a failure and retries up to the attempt limit.
- The skill author controls the hook's flags, not the person using the skill. Unless the skill passes `--anonymous`, the git email is sent; that person can keep it off the wire by setting `COOLHAND_CAPTURE_USER` in their own environment to any other identifier.
- A session left idle for more than 30 days can lose its progress file (it is pruned when another session starts), so if it is continued, turn numbering restarts at 1. `metadata.turn_id` still differs per turn.
- Progress per session lives in `~/.coolhand/capture-turns/` (files untouched for 30 days are removed whenever a new session starts). A hook that fires twice for one turn sends it once in the normal case (see the duplicates note above); two genuinely identical turns are told apart by Claude's request id.

## VS Code Copilot: spike findings

Recorded on 2026-11-02 from a real VS Code GitHub Copilot agent-mode session (Copilot SDK harness, `copilotVersion` 1.0.103) with a throwaway recorder hook in `.github/hooks/`. One three-turn skill session and one unrelated chat; redacted payloads and transcripts are in `test/fixtures/copilot/`. Everything not listed here is still unverified, including Windows behaviour (the PowerShell command was never run).

| Question | Finding |
|---|---|
| Does a hook file in `.github/hooks/*.json` run? | Yes, for every chat in the workspace, including ones that never used the skill. |
| Can a skill declare its own hooks? | No. `hooks:` in `SKILL.md` frontmatter was silently ignored (none of its commands ran). |
| Event names | Both camelCase (`agentStop`, `userPromptSubmitted`, …) and PascalCase (`Stop`, `UserPromptSubmit`, …) are honoured. Registering both runs every hook twice. |
| Payload shape | PascalCase events get Claude-style snake_case JSON: `hook_event_name`, `session_id`, `cwd`, `timestamp` (ISO), and for `Stop` also `transcript_path`, `stop_reason`, `stop_hook_active`. camelCase events get `sessionId`, `transcriptPath`, `stopReason`, with a numeric `timestamp`. |
| `Stop` / `agentStop` | Fires once per user message, when the agent loop ends (three messages gave three `Stop`s). It carries no assistant text; read it from the transcript. |
| `UserPromptSubmit` | Carries `prompt`. For a skill invoked by slash command that is the expanded text containing `<skill-context name="…">`; later messages in the same chat are just what the user typed. |
| Tool events | `PreToolUse` / `PostToolUse` carry `tool_name`, `tool_input` and `tool_result`. |
| `transcript_path` | `~/.copilot/session-state/<session_id>/events.jsonl`, typed JSONL: `session.start`, `skill.invoked` (`name`, `path`, `invokedAtTurn`, `trigger`), `user.message`, `assistant.message` (`content`, `toolRequests`), `tool.execution_start` / `_complete`, `assistant.turn_start` / `_end`, `session.usage_record` (token counts), `hook.start` / `_end`. |
| Does the transcript lag the hook? | Not in this run: each reply was in the file 15 to 20 ms before `Stop` fired. Three samples, so keep the lag guard. |
| Skill invoked? | A chat that used the skill has a `skill.invoked` event with the skill name; the unrelated chat's transcript has none. This is the gate for capturing only skill sessions. |
| Session env var | None. Hooks get `COPILOT_PROJECT_DIR`, `COPILOT_HOOK_DIR`, `COPILOT_HOME` and `AI_AGENT=github_copilot_vscode_agent`, not the session id. |
| Command keys | `bash` was used and worked on macOS. `command` and `powershell` are documented by VS Code but were not tested. |
